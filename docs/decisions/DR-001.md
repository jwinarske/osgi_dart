# DR-001 — Third-party bundles cannot be isolated in-process

**Date:** 2026-08-11 · **Status:** accepted (constraint), open (mitigation)
**Supersedes:** the "FFI everywhere" direction taken earlier the same day.

> Moved here from the project plan on 2026-09-11. File citations are to
> ivi-homescreen `v3.0`; the ones marked *rechecked* at the end were verified
> again at `cb0057b2` (2026-08-11).

## Question

The bundle-to-shell handshake can run over the `dev.osgi/bridge` MethodChannel
or over an FFI surface exported from `libihs_shared.so`. FFI was preferred on
build-dependency grounds: a MethodChannel forces `package:flutter` into every
bundle's package graph, including headless service bundles that have no views,
so `dart analyze` and `dart test` need the Flutter SDK to run at all.

Then third-party bundle loading was raised as a goal, which changes what the
transport has to be answerable for.

## What was checked

| Claim | Evidence (ivi-homescreen) |
|---|---|
| The full host ABI is reachable by anything in the process | `shared/ihs_shared.map` exports by glob: `global: ihs_*; FlutterDesktop*;` — ~72 symbols |
| Bundles already hold `dart:ffi` today | The MethodChannel activator uses `NativeApi.initializeApiDLData` and `SendPort.nativePort`, both from `dart:ffi` |
| Shell-only seams are exported like everything else | `ihs_semantics_set_host`, `ihs_pv_set_host`, `ihs_trace_set_engine_procs`, `ihs_flutter_desktop_set_procs` — all documented "SHELL-ONLY", all matched by the `ihs_*` glob |
| A capability-table lookup already exists | `ihs_get_api(requested_abi)` returns `IhsApi` with NULL sub-tables for absent capabilities (`shared/include/ihs/ihs.h`) |
| Two sharp surfaces are already build-gated off | `BUILD_ACCESSIBILITY` (semantics) and `BUILD_MCP` both default OFF (`shared/CMakeLists.txt:35-41`) |
| Location is **not** gated | `target_sources(ihs_shared PRIVATE src/location/...)` unconditional at `shared/CMakeLists.txt:203` |
| The channel already knows who is calling, and ignores it | `OsgiBridgePlugin` is one instance per engine (`flutter_desktop_engine_state.h:92`, constructed `flutter_desktop.cc:130`) but `HandleMethodCall` is `static` and reads `symbolic_name` from the call arguments |

## Finding

**No in-process capability scheme is a security boundary against a bundle that
holds `dart:ffi`.**

A proc-address design in the style of `eglGetProcAddress` — a small
authenticated surface that vends function pointers for granted capabilities —
was considered. `ihs_get_api()` is already that shape. It fails as a boundary
for reasons that are not fixable by tightening it:

- `Pointer.fromAddress(n).cast<Uint8>().asTypedList(len)` is arbitrary read and
  write over the whole address space: the capability table itself, the bundle
  registry, other bundles' isolate heaps.
- `DynamicLibrary.open('libc.so.6')` yields `dlsym`, `mmap`, `mprotect`,
  `execve`. No grant required; it is an ordinary library.
- Hiding a symbol does not hide its code. `/proc/self/maps` plus the on-disk ELF
  turns a non-exported function into pointer arithmetic.
- **Granted pointers are transferable and irrevocable.** A bundle can send a
  capability's address to another bundle as an `int` over a `SendPort`.

OSGi's own permission model worked because the JVM verified bytecode and denied
arbitrary memory access. Dart AOT provides no equivalent, so the model does not
port. Making `ihs_get_api()` authoritative would additionally require moving
`ihs_*` out of the version script's `global:` glob, breaking every out-of-tree
consumer, the installed headers, the CMake export target, and the pkg-config
file — for a boundary that still would not hold.

## Consequences

**1. Both transports stay. This is a security requirement, not a convenience.**
An FFI transport requires every bundle to hold `dart:ffi`, which is precisely
the capability an untrusted bundle must not have.

| Tier | Transport | `dart:ffi` | Notes |
|---|---|---|---|
| First-party / signed | FFI (`ihs_osgi_*`) | yes | Pure-Dart package graph, no platform-thread coupling on the ACTIVE report |
| Third-party | MethodChannel only | **no** | Slower; see cost below |

**2. MethodChannel has unforgeable caller identity, and the shell is discarding
it.** The plugin instance belongs to one engine, and the shell created that
engine for a specific bundle — so the caller is known by construction, with
nothing for a bundle to pass to another bundle. Binding identity to the owning
engine instead of trusting the `symbolic_name` argument is strictly stronger
than the handle-capability drafted in `ihs_osgi.h`. **Worth doing regardless of
the rest of this record:** today any bundle can report ACTIVE for any other
bundle over the channel, which silently releases a critical bundle's startup
wait.

**3. An ffi-free tier costs the fast paths.** `NativeApi.initializeApiDLData`
and `SendPort.nativePort` are both `dart:ffi`, so for untrusted bundles the
shell must deliver the framework port over the channel rather than via
`Dart_PostCObject_DL`, and inter-bundle traffic must use channels too. That
gives up "off the platform thread, no channel on the hot path" — and gives up
the shared-VM and cross-isolate-pointer properties that the zero-copy transport
work assumes.

**4. Enforcement is unsolved and dominates the design.** Denying `dart:ffi`
counts only if it can be verified. Against a prebuilt third-party `libapp.so`,
static verification of an AOT snapshot is adversarial and unreliable. That
leaves two options:

- **Compile third-party bundles from source** and reject `dart:ffi` imports at
  build time. Keeps the shared-VM design. Requires source access.
- **Process isolation** — one process per untrusted bundle, capabilities across
  an IPC boundary. The only option that holds against a prebuilt hostile bundle.
  It costs the shared VM entirely, so `SendPort` and cross-isolate pointers stop
  working between tiers, and `FlutterEngineAddView` is the wrong mechanism: an
  isolated bundle renders to its own surface and the shell composites it.

## Open decision

Which enforcement model applies to third-party bundles. **This should be settled
before the framework's shape is fixed**, because process isolation invalidates
the shared-VM assumption that the service registry, the framework isolate, event
admin and the zero-copy transport are built on — and this repository currently
assumes bundles share a VM.

## Not yet frozen

`shared/include/ihs/ihs_osgi.h` and `ihs_osgi_host.h` are **wired in and
exported** as of ivi-homescreen #538: `ENABLE_OSGI` compiles
`shared/src/osgi_api.cc` into `ihs_shared`, and `ihs_osgi.h` is installed only in
that configuration (`ihs_osgi_host.h` never — it is a shell-only seam). The
prediction about `ihs_shared.map` held: the `ihs_*` glob exported all seven entry
points with no change to the version script, so `ENABLE_OSGI` is the only gate on
that surface, the same lever `BUILD_MCP` uses.

The shell-side host landed in ivi-homescreen #540: `osgi_host` installs the
`IhsOsgiHost` table over `BridgeRegistry`, so both transports end at one
registry, and the declared-name check gates the FFI path without being written
twice. A bundle reports through an opaque handle the registry mints — 64 random
bits, never derived from the name, the port, or an index, and never
dereferenced by either side — rather than through a name any caller could
supply.

That is consequence 2's remedy on this path, and it is stronger than what the
channel offers: over FFI a bundle can only report for *itself*, because the
capability is the registration. The channel still reads `symbolic_name` from the
call, so a declared bundle can still report for another declared one.

What remains unproven is the handshake with a live Dart VM. Every test on either
side fakes the other: the shell suites fake the Dart DL calls, the forwarder
suite fakes the host, and `osgi_ffi` is tested against a fake of the C surface.
The first real FFI handshake needs a Dart bundle and this shell together on
hardware. The means to do one now exists — ivi-homescreen #544 taught
`test/integration/osgi_activator_test` to speak either transport, selected by
`TRANSPORT=channel|ffi` in `test/osgi_multi_bundle.sh` — so what is missing is a
run on a rig with two connected outputs and DRM master, not the harness for it.

## Rechecked 2026-09-11 (ivi-homescreen `cb0057b2`)

- **Consequence 2 still stands.** `OsgiBridgePlugin::HandleMethodCall` is still
  `static` and takes `symbolic_name` from the arguments for `init`, `active`,
  `stopped` and `shutdown` (`shell/osgi/osgi_bridge_plugin.cc:73-187`).
- **A related gap: a name absent from the config was not refused either — closed
  by ivi-homescreen #537.** `init` used to accept any non-empty name that was not
  already registered; a later `active` under that name passed the bridge, and the
  orchestrator logged "ACTIVE reported by unknown bundle" and dropped it. The
  bundle saw success while the configured bundle's critical wait expired.
  `BridgeRegistry` is now given the declared `symbolic_name`s at bring-up and
  refuses a registration naming anything else, so the typo fails at the call that
  made it. Gating registration gates the reports too, since `ReportActive`
  already requires one. Consequence 2 is untouched: a *declared* bundle can still
  report for another declared bundle.
- `ihs_osgi.h` and `ihs_osgi_host.h` are still untracked in the local clone and
  not wired into CMake.
